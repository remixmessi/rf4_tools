# RF4 服务端项目分析与工具整合包规划

## 1. 分析目标与范围

基于现有 `rf4_server_simulator` 服务端，规划面向本地/局域网模拟器环境的游戏工具整合包。Windows 客户端资源和运行逻辑将在后续阶段分析。

计划功能：

1. 修改渔轮、鱼竿等装备参数。
2. 修改渔轮、鱼竿的模型和皮肤。
3. 定制装备。
4. 上鱼雷达：显示每根鱼竿的上鱼信息。
5. 人物移速修改。
6. 灯光照亮范围编辑。

### 路径

- 工具项目：`/Users/yixuli/myProject/myGame/rf4_tools`
- 用户提供的服务端目录：`/Users/yixuli/myProject/myGame/rf4_server_simulator`
- 实际服务端源码根目录：`/Users/yixuli/myProject/myGame/rf4_server_simulator/rf4_server_simulator`

下文源码定位均相对于实际服务端源码根目录。行号对应本轮分析时的源码，后续更新可能变化。

### 验证边界

本轮已完成源码、管理路由、装备生成链路、钓鱼状态链路和静态数据库的只读检查。

- 未修改服务端源码、数据库或执行装备修改脚本。
- 未启动服务端或运行 Windows 客户端验证。
- 当前环境 `PATH` 中没有 Go 编译器，未执行编译或测试。
- README 标注兼容目标为客户端 **4.0.25034**；后续应先核对实际客户端版本。
- 文档中的“建议新增”属于设计方案，不代表现有功能。

## 2. 总体结论

该项目适合作为工具整合包的服务端基础，但六项功能不能全部只靠服务端实现。

建议采用：

> 统一工具界面 + 服务端扩展 + Windows 客户端适配。

优先实现上鱼面板、已确认装备字段的编辑和基于现有装备的定制预设。模型皮肤、移速、灯光及部分装备参数的客户端效果，需要完成 Windows 客户端分析后再确认实现路径。

## 3. 项目架构与可复用能力

```text
Windows 游戏客户端
    ↓
gateway：登录、连接、协议加解密
    ↓
gameserver：装备、钓鱼、物品与结算
    ↓
SQLite：玩家数据 + 只读静态游戏配置

launcher：服务进程管理 + 内嵌 Web 管理后台
```

标准 launcher 入口为 `http://127.0.0.1:9500`，管理后台挂载在 `/admin/`，其 API 使用 `/admin/api/*`。独立管理进程内部仍使用 `/api/*` 路由。

现有可复用能力：

- JWT 鉴权、管理 API、物品发放、操作审计。
- 装备定义、装备实例、子部件装配、物理属性处理。
- 按玩家、按鱼竿保存的钓鱼状态。
- 协议编解码和类型表。
- 服务进程管理、日志和运行控制。

只读查询 `server_data/static.sqlite3` 的结果：

| 类型 | 定义数量 |
| --- | ---: |
| 全部物品 | 16,434 |
| 鱼竿（category=3） | 1,043 |
| 渔轮（category=6） | 720 |

这些是数据库定义条数，不等同于当前客户端全部可购买或可正常使用的装备数量。

主要参考：`docs/architecture.md`、`docs/admin-console.md`、`README.en.md`。

## 5. 装备参数修改

### 5.1 已确认的数据基础

`internal/store/repos2.go:495` 定义了 `ItemDef`，包含：

- `NumericID`
- `ItemID`
- `Category`
- `Kind`
- `Brand`
- `AttrsJSON`

`internal/gameserver/gear_physics.go:18` 定义并读取多种装备参数：

| 装备 | 已识别参数示例 |
| --- | --- |
| 鱼竿 | 强度、长度、调性、硬度、刚度、灵敏度 |
| 渔轮 | 摩擦片最大曳力、齿轮传动比及多种子部件配置 |
| 鱼线、前导线 | 强度、直径、长度等 |
| 装备实例 | 耐久、工艺及其派生物理字段 |

其中，刚度和灵敏度在源码注释中被标记为客户端表现相关、服务端只记录，不能把“存在字段”当成“服务端修改一定改变客户端手感”。

### 5.2 关键约束

#### 浮点数可能以整数位型保存

部分 `attrs_json` 数值是 IEEE754 float32 的 uint32 位型，并非其表面整数值。

例如：

- `kngaaefkpka`：通用强度字段。
- `mlfjkaoicdn.omghfmdfjpc`：摩擦片最大曳力。
- `oiaplokhcii.dpgbopbanal`：齿轮传动比。

工具界面应提供 kg、m、倍率等人类可读值，由适配层完成编码、解码和范围检查。不能对所有数字统一进行浮点位型转换，枚举和普通整数需要单独定义。

#### 静态装备库运行期只读

服务端将 `static.sqlite3` 以只读方式挂载，并通过临时视图读取静态表。主玩家库中的兼容副本会被视图遮蔽，直接修改该副本可能不影响运行时结果。

参考：`docs/static_runtime_isolation.md`。

#### 修改实例快照可能被重建覆盖

`internal/gameserver/items.go:299` 的 `ItemToTree` 会：

1. 读取物品实例字段。
2. 获取装备定义。
3. 物化嵌套子配置。
4. 根据权威定义、耐久和工艺重新投影物理字段。
5. 重建鱼竿挂载部件和钓组。

因此，只修改一次实例 JSON 并不能保证修改长期生效。

#### 客户端可能读取自己的定义

现有代码显示部分部件和属性由客户端按数字 ID 查找本地定义。服务端计算值改变，不等于客户端显示、物理和手感全部同步改变。

### 5.3 建议新增的覆盖机制

```text
原始装备定义
    ↓
全局模板覆盖
    ↓
单件装备实例覆盖
    ↓
统一生成服务端计算值和下发数据
```

建议：

- 保持原始静态库不变，覆盖数据单独持久化。
- 明确“修改所有同型号装备”和“只修改这一件装备”的作用域。
- 统一接入物理计算和协议投影，避免两套数值不一致。
- 提供恢复默认、变更预览、备份和审计。
- 对客户端本地读取的字段另行设计客户端适配。

上述覆盖层是建议新增能力，不是现有项目已经完整实现的功能。

## 6. 模型与皮肤修改

建议拆分三个目标：

| 层级 | 内容 | 主要验证点 |
| --- | --- | --- |
| 换贴图/材质 | 保持模型和动作，替换外观 | 材质与贴图加载方式 |
| 换已有模型 | 使用客户端已有另一套模型 | 模型映射、挂点和部件兼容 |
| 导入新模型 | 新增资源与加载映射 | 资源格式、动画、挂点和加载路径 |

建议先从贴图或材质替换开始。

不能把修改 `numeric_id` 或 `item_id` 当成纯换肤，因为这可能同时改变属性、类别、部件和客户端定义。

目标应是分离：

```text
装备身份与属性：原装备或定制属性
视觉外观：独立选择的替换资源
```

待 Windows 客户端验证：

- 引擎版本和运行时类型。
- 装备 ID 到模型、材质、贴图的映射方式。
- 资源格式与加载入口。
- 是否已有可复用的独立外观字段。
- 换场景、重新装备、重新登录后的重载行为。

目前没有依据承诺只改服务端就能替换模型。

## 7. 定制装备

### 7.1 建议分级

| 级别 | 内容 | 判断 |
| --- | --- | --- |
| 现有装备预设 | 选择已有竿、轮、线，组成套装并发放 | 基础较完整，需补工具流程 |
| 单件属性定制 | 只改特定 GUID 对应装备 | 需要实例覆盖机制 |
| 外观与属性组合 | 指定外观加自定义参数 | 需要客户端配合 |
| 全新装备 | 新 ID、名称、模型与配置 | 需要双端支持 |

### 7.2 现有发放接口

标准 launcher 下：

```text
POST /admin/api/players/grant
```

当前参数：

```json
{
  "uid": 1000001,
  "item_id": "已有物品标识",
  "qty": 1
}
```

该接口将发放任务放入共享队列，由 gameserver 执行，以维持在线状态一致性。它不是任意属性定制接口。

参考：`internal/admin/api.go:660`。

第一版建议基于客户端已认识的装备定义制作预设，避免直接添加客户端不认识的数字 ID。

## 8. 上鱼雷达／每杆上鱼面板

### 8.1 已有核心数据

服务端通过玩家 UID 和竿 GUID 管理多杆状态。工具应以 `UID + 竿GUID` 为行标识，并用鱼 GUID 区分鱼，不能只跟踪当前手持竿。

已确认可获取：

- 鱼竿、钓组和钩 GUID。
- 鱼 GUID、鱼种键、等级、重量、长度。
- 是否已派鱼、是否确认中钩、是否结算。
- 地图、钓深、抛距、落点等上下文。
- 多钩的额外鱼及待处理渔获。

参考：

- `internal/gameserver/fishing_rods.go:12`
- `internal/gameserver/fishing.go:21`
- `internal/gameserver/fishing.go:273`

### 8.2 事件语义

| 事件/协议 | 含义 | 注意事项 |
| --- | --- | --- |
| `14/14` | 派鱼/咬口阶段 | 不等于已经刺中鱼 |
| `14/11` | 中钩确认处理 | 仍可能因保持率等逻辑失败 |
| `14/12` | 客户端鱼状态反馈 | 不同状态码含义不同，不能统一判为脱钩 |
| `14/15` | 鱼离场推送 | 不是中钩确认 |
| 入护、放生成功 | 清理并结束相应状态 | 面板需要同步清理 |

普通路径是在咬钩判定时生成本次鱼，因此本功能是“每杆上鱼信息”，不是扫描地图上全部野生鱼。

### 8.3 多杆、多钩和耐力限制

- `Pending`、`Extra`、`Batch` 等字段分别承载主鱼、额外钩鱼和待处理鱼。
- 额外钩鱼可能没有独立实体推送，只监听 `14/14` 可能漏鱼。
- 部分额外鱼状态仅在内存中，不能假定数据库快照包含全部实时信息。
- 当前耐力播报依赖客户端上报，主要针对当前手持且正在搏鱼的竿。
- 不能承诺所有非手持竿都有连续、准确的鱼耐力数据。
- 离线不一定清鱼，重连可能恢复原状态，应单独显示离线和数据陈旧标记。

参考：`internal/gameserver/gear_assistant_stamina.go:3`、`internal/store/repos_fishing_state.go:11`。

### 8.4 API 现状与建议

现有后台没有每杆实时鱼状态 API。

- 玩家详情接口不是实时上鱼接口。
- 鱼池、鱼口配置接口不是当前咬钩鱼列表。
- 竿架报警器配置不是外部雷达订阅接口。

建议新增只读快照能力，由 gameserver 提供权威多杆状态，通过内部通道接入已鉴权的管理接口。第一版可以定时查询快照，后续再按需要增加事件推送。

```text
鱼竿 A：等待咬口
鱼竿 B：已派鱼，尚未确认中钩
鱼竿 C：搏鱼中｜鱼种｜重量｜长度
```

必须覆盖的状态：

- 等待咬口、已派鱼、中钩、搏鱼、待入护/放生。
- 跑鱼、拒收、断线、重连和状态过期。
- 多钩鱼和迟到反馈。

还需在客户端验证 UI 中第几根竿、快捷键、竿架槽位与竿 GUID 的对应关系。

## 9. 人物移速修改

本轮在服务端 Go 实现中没有找到直接控制步行速度、奔跑速度或移速倍率的接口。这个结论不等于证明协议绝无尚未识别的相关字段。

暂归入客户端适配模块，待验证：

- 移动控制器和速度参数的位置。
- 步行、奔跑、负重、体力之间的关系。
- 服务端是否限制位置变化。
- 切换地图、重生或重新登录后是否重置。

不建议用全局时间倍率替代移速修改，以免影响钓鱼物理、动画和计时。

## 10. 灯光照亮范围编辑

本轮找到手电相关装备枚举，但没有找到服务端控制照射范围的实现或 API。

客户端分析应区分：

- 手电、头灯、营地灯。
- 光照距离、亮度和聚光角度。
- 阴影距离与渲染限制。

“更亮”不等于“照得更远”。建议第一版独立提供范围、强度、角度及恢复默认能力，具体支持字段以客户端验证为准。

## 12. 推荐实施顺序与验证目标

### 阶段一：每杆上鱼面板

- 新增只读多杆快照接口。
- 实现每杆状态和鱼信息显示。
- 验证切杆、多杆、多钩、跑鱼、入护、放生、断线与重连。
- 确保已派鱼与已中钩分开显示，旧数据不会持续冒充实时状态。

### 阶段二：装备参数编辑

- 建立字段字典：语义、单位、类型、范围、服务端/客户端归属。
- 支持少量已确认参数及恢复默认。
- 建立独立覆盖存储和统一解析入口。
- 验证服务端计算、下发值、客户端显示和实际表现是否一致。

### 阶段三：定制装备预设

- 基于现有装备生成与发放。
- 区分全局模板覆盖和单件实例覆盖。
- 验证装配、修理、重登和物品树重建后定制是否保留。

### 阶段四：客户端适配

- 分析资源与运行时。
- 先验证简单换肤，再推进模型替换。
- 实现并验证移速、灯光和客户端参数同步。
- 为不同客户端版本明确兼容性和恢复路径。

## 13. Windows 分析准备清单

1. 客户端准确版本号、服务端版本或提交号。
2. 客户端安装目录结构。
3. 程序、运行库、数据目录和资源包的文件清单。
4. 一根鱼竿、一个渔轮的明确名称，作为固定测试对象。
5. 单竿、多竿、切换手持、跑鱼、入护的操作记录和日志。
6. 修改前可恢复的客户端与存档备份。

后续分析应先做单变量对照，记录修改前后显示值、协议值和实际效果，避免把只改变 UI 或仅改变服务端计算的结果误判为完整生效。

## 15. 当前结论与剩余依赖

可以先推进每杆上鱼面板和装备管理的服务端设计。客户端外观、移速、灯光及部分装备参数的实际生效方式，依赖后续 Windows 客户端分析。

本轮结论来自静态代码与数据库检查，不代表已完成运行验证；正式实施后还需补充服务端测试和客户端实机回归。
