# RF4 工具整合包：开发技术与项目结构

> 当前阶段更新：只确定 UI 设计，暂停正式前端与游戏逻辑开发，等待 Windows 客户端分析。已选 A 双工作空间为主结构；D 作为保存后的修改记录和回滚入口，不做修改前审批。编辑页直接保存，默认亮色，可切换配色。以《UI设计定稿.md》和 `doc/design/index.html` 为当前依据，后文技术栈与工程目录仅为后续建议。

## 1. 产品目标

工具包同时提供 Web 版和 Windows 桌面版，共用前端界面、业务模型和功能接口。

必须区分两个运行位置：

- 服务端：可运行在 Windows、Linux、macOS 或 Docker 中。
- 游戏客户端：运行在 Windows 上，可能与服务端位于不同设备。

不能假设工具、游戏客户端和服务端在同一台电脑，也不能将服务端未连接与客户端未连接合并为一种状态。

本文是开发方案，不代表相关模块已实现。六项游戏功能的源码分析与限制见同目录的《项目分析与工具整合包规划.md》。

## 2. 产品形态

### 2.1 Web 管理端

浏览器访问工具界面，连接本地或远程服务端。

主要承载：

- 服务端连接和状态展示。
- 装备参数、定制预设和物品发放。
- 每杆上鱼信息。
- 服务端侧配置与操作记录。
- 客户端相关功能的配置界面；实际执行需要连接 Windows 本地助手。

Web 静态文件可以通过独立静态服务器、反向代理或 Docker 部署。浏览器所在平台不决定服务端所在平台。

### 2.2 Windows 桌面增强端

使用同一套前端，增加桌面和客户端本地能力：

- 游戏目录选择与检测。
- 本地资源读取、备份和替换。
- 游戏进程检测及启动。
- 与客户端扩展通信。
- 独立置顶上鱼窗口。
- 托盘、窗口管理和可选全局快捷键。

桌面壳本身不会自动实现移速、灯光或游戏资源替换。具体能力仍依赖客户端分析和本地适配实现。

### 2.3 功能分工

| 功能 | Web 版 | Windows 桌面版 |
| --- | --- | --- |
| 连接本地或远程服务端 | 支持 | 支持 |
| 装备服务端参数编辑 | 支持 | 支持 |
| 定制预设与物品发放 | 支持服务端部分 | 支持，可联动本地能力 |
| 每杆上鱼面板 | 支持 | 支持，可独立置顶 |
| 模型、皮肤替换 | 需要 Windows 本地助手 | 通过本地适配模块执行 |
| 人物移速、灯光修改 | 需要 Windows 本地助手 | 通过本地适配模块执行 |
| 本地目录与进程管理 | 需要 Windows 本地助手 | 通过桌面/本地接口执行 |
| 托盘与全局快捷键 | 不作为浏览器原生能力 | 可实现 |

表格为目标能力划分。真实可用字段和操作以服务端、客户端能力探测及实机验证结果为准。

## 3. 技术选型

| 层级 | 推荐方案 | 当前决策状态 |
| --- | --- | --- |
| 前端框架 | React + TypeScript | 推荐作为第一阶段基础 |
| 开发与构建 | Vite | 推荐 |
| 页面路由 | React Router | 建议，实施时确定版本 |
| 远程数据状态 | TanStack Query | 接入真实接口时按需要引入 |
| 表单与数据校验 | 类型化字段定义；可使用 Zod | 统一约束，具体依赖实施时确定 |
| 视觉样式 | CSS 变量设计令牌 + 组件样式 | 先统一颜色、间距、字号和状态 |
| UI 模拟数据 | TypeScript Mock 适配器 | 第一阶段使用 |
| 服务端接口 | 扩展现有 Go 管理 API 和 gameserver 内部数据通道 | 复用现有服务端能力 |
| Windows 桌面壳 | 优先评估 Tauri 2，Electron 备选 | 客户端分析后最终确定 |
| Windows 本地助手 | 独立本地进程或可复用模块 | 通信方式和实现语言待验证 |
| Web 部署 | 静态文件 + 同源反向代理；可容器化 | 真实接口阶段实现 |

不在 UI 阶段固定客户端插件框架、资源解析库或运行时修改方案。

### 3.1 桌面壳取舍

Tauri 2 通常具有较小的分发体积，Windows 使用 WebView2，本地能力可通过 Rust 或独立辅助进程提供。

Electron 使用 Chromium 和 Node.js，JavaScript/TypeScript 生态成熟，但安装体积与内存占用通常更大。

最终选型需验证：

- 客户端扩展的通信方式。
- 多窗口、置顶、透明窗口等实际需求。
- 安装、升级、WebView2 依赖和故障恢复。
- 本地辅助进程的打包与生命周期管理。

普通独立置顶窗口优先于游戏内叠加层；独占全屏下的可见性不能仅凭“置顶”保证，需要实测。

## 4. 总体架构

```text
Web 浏览器                      Windows 桌面壳
    │                                │
    └──────────── 共用前端 ────────────┘
                     │
              类型化功能接口
              /             \
             ↓               ↓
       服务端适配器       客户端/宿主适配器
             │               │
       已鉴权管理 API    Windows 本地助手或桌面桥接
             │               │
       gameserver       Windows 游戏客户端
             │
       玩家数据与状态

服务端可部署于 Windows / Linux / macOS / Docker
```

### 4.1 前端界面层

负责页面、表单、交互和状态展示，不直接读取 SQLite，不直接操作游戏进程，不直接调用散落在组件中的桌面专属 API。

### 4.2 业务模型与契约层

负责：

- 装备、预设、鱼竿、鱼、连接状态等模型。
- 字段类型、单位、范围和能力描述。
- 查询与命令的输入输出。
- 错误类型、执行状态和刷新约定。

### 4.3 适配层

提供同一组接口的不同实现：

- Mock：界面开发与交互演示。
- HTTP：服务端管理 API。
- Local helper：浏览器连接 Windows 本地助手。
- Desktop bridge：桌面壳的本地能力。

组件依赖接口，不依赖具体传输方式。桌面和 Web 复用业务语义，但不强求它们使用完全相同的底层通信机制。

### 4.4 服务端扩展

优先复用既有鉴权、命令队列、物品生成和审计。

需要新增的主要能力：

- 装备字段与有效参数查询。
- 参数覆盖规则的保存、校验与应用。
- 单件装备或套装定制命令。
- 从 gameserver 获取实时多杆状态。
- 能力与版本信息。

管理 API 和 gameserver 是不同职责，不能假设管理 HTTP handler 可以直接读取另一个进程的内存。每杆实时状态需要明确的内部通信通道，不能只靠数据库历史快照。

## 5. 推荐目录结构

以下是目标结构，按阶段逐步创建，不要求第一阶段创建空的桌面或助手工程。

```text
rf4_tools/
├─ doc/
│  ├─ 项目分析与工具整合包规划.md
│  └─ 开发技术与项目结构.md
├─ apps/
│  ├─ web/                       # React 页面、路由和应用入口
│  │  ├─ src/
│  │  │  ├─ app/                 # 应用组装、布局、路由
│  │  │  ├─ pages/               # 各功能页面
│  │  │  ├─ features/            # 功能交互、表单与视图模型
│  │  │  ├─ components/          # 跨页面组件
│  │  │  └─ styles/              # 设计令牌与全局样式
│  │  └─ public/
│  └─ desktop/                   # 后续桌面宿主配置与原生桥接
├─ packages/
│  ├─ contracts/                 # 模型、字段和接口契约
│  ├─ adapters/                  # Mock、HTTP、本地和桌面适配
│  └─ fixtures/                  # 演示数据与场景
├─ services/
│  └─ windows-helper/            # 后续本地助手，技术待确认
├─ deploy/                       # Web 容器与反向代理配置
└─ package.json                  # 工作区脚本与依赖管理
```

桌面宿主加载共用前端构建产物，不复制一套页面源码。服务端 Go 扩展仍维护在对应服务端仓库中，本仓库保留协议契约与兼容说明，不复制整个服务端项目。

## 6. 页面与交互设计

| 页面 | 第一阶段内容 |
| --- | --- |
| 总览 | 双连接状态、版本信息、能力摘要、快捷入口 |
| 装备参数 | 搜索分类、装备选择、参数编辑、修改对比、恢复默认 |
| 外观管理 | 模型/皮肤列表、外观选择、资源信息、占位预览 |
| 定制装备 | 基础装备选择、参数与外观组合、预设保存及导入导出 |
| 上鱼雷达 | 多杆卡片、阶段状态、鱼信息、数据更新时间 |
| 人物与灯光 | 移速、灯具、范围、亮度、角度的配置界面 |
| 设置 | 服务端连接、本地助手配对、路径、版本、备份入口 |

视觉方向：亮色桌面工具风格，A 双工作空间与侧栏组织功能；D 仅保留保存后的前后值记录与回滚，不作为修改前审批。默认海蓝，可切换森林绿、暖砂等亮色主题，状态与危险操作保留独立语义。

同时考虑浏览器窗口缩放和桌面窄窗口。真实模型预览暂不实现，用明确的占位区域展示，不能伪装成已加载游戏资源。

## 7. 双连接与能力驱动

示例：

```text
服务端：已连接 · Linux / Docker
客户端助手：未连接
运行模式：演示模式 / 真实连接
```

### 7.1 连接状态分别管理

每个连接独立包含：

- 未配置、连接中、已连接、连接失败、已断开。
- 版本与兼容性状态。
- 最后成功通信时间。
- 可用能力。

本地助手在线也不等于游戏正在运行，应进一步区分游戏未启动、客户端扩展未加载和能力就绪。

### 7.2 按能力启用功能

能力名称可按以下方向设计，最终名称以接口实现为准：

```text
equipment.read
equipment.override
inventory.grant
fishing.snapshot
appearance.apply
player.speed
lighting.edit
host.game.launch
```

功能不可用时说明实际原因：服务端未连接、需要本地助手、版本不支持或能力尚未实现。不能仅按操作系统名称判断能力。

## 8. 参数与预设模型

### 8.1 参数配置驱动

每个字段至少描述：

- 稳定字段标识和显示名称。
- 类型：数字、枚举、布尔等。
- 单位、精度、范围与默认值。
- 支持状态与读写能力。
- 作用域：全局装备模板或单件实例。
- 来源：服务端、客户端或需要双端同步。

前端使用人类可读数值；协议混淆字段名和 float32 位型转换放在适配层，不暴露给普通操作流程。

### 8.2 预设持久化

第一阶段可保存工具预设和偏好，并支持 JSON 导入导出。

预设应包含 schema 版本，以便后续迁移。预设文件不保存账号密码或访问令牌。应用预设前重新检查当前版本、字段和能力，不能将历史预设直接视为有效游戏配置。

## 9. 模拟数据与真实执行边界

第一阶段所有游戏交互使用 Mock 适配器，并明确显示：

> 演示模式：当前操作不会修改游戏。

可以真实实现的工具侧功能：

- 导航、搜索、筛选和排序。
- 参数表单、校验、修改对比和重置。
- 工具预设本地保存、导入和导出。
- 多杆状态模拟与异常场景切换。

未接入游戏的操作只能显示“模拟执行”或“尚未接入”，不能提示真实发放或应用成功。

演示数据与真实连接数据分离，切换模式时清理或隔离缓存，避免把模拟鱼、模拟装备或未提交草稿显示为真实状态。

## 10. 接口与命令状态

### 10.1 查询和命令分开

- 查询：装备目录、有效参数、玩家物品、多杆快照和能力信息。
- 命令：保存覆盖、应用定制、发放、替换资源和修改客户端参数。

已有发放接口是队列模式。HTTP 请求成功不等于游戏端执行完成，界面应区分“已受理”“执行中”“执行成功”“执行失败”。实际完成反馈需要服务端提供对应能力；缺少反馈时只能展示已受理。

### 10.2 雷达数据

以玩家 UID 与鱼竿 GUID 标识杆，以鱼 GUID 区分鱼，支持一杆多鱼。

快照应提供更新时间、在线状态和阶段信息。初期可轮询，后续根据需要增加事件推送；断线重连后重新拉取完整快照，避免漏事件导致状态残留。

已派鱼与已中钩必须分开，耐力数据缺失或过期时不显示为可靠实时值。

## 11. 部署与本地助手连接

### 11.1 Web 部署

优先使用同源反向代理：

```text
浏览器 → Web 入口
            ├─ 静态页面
            └─ API 代理 → 服务端管理接口
```

远程管理保留鉴权，按部署环境配置 HTTPS。代理保持实际管理路由语义，不擅自将已有 `/admin/api/*` 改为未经实现的新接口。

远程浏览器中的 `localhost` 指浏览器所在电脑，不是 Docker 容器或远端服务器。连接设置和部署说明必须明确这一点。

### 11.2 Windows 本地助手

Web 版访问本地助手时，需要验证 HTTPS 页面访问本地服务、浏览器本地网络访问策略及混合内容限制，不能假设所有浏览器可无条件连接。

本地助手应默认只提供本机访问，通过明确配对、来源校验和受限操作接口授权。不要提供任意路径写入或任意命令执行接口。

桌面版可使用原生桥接访问同一套本地业务模块。Web 与桌面应复用能力定义，但通信实现可以不同。

## 12. 分阶段开发路线

### 阶段一：UI 与可交互原型

- 建立 React、TypeScript、Vite 工程。
- 完成设计令牌、统一布局、双连接状态和演示模式。
- 优先完成装备参数页和上鱼雷达页。
- 补齐其余页面、预设管理和异常状态。
- 使用 Mock 适配器，不依赖客户端分析完成。

验收：页面可操作、模拟状态清晰、预设可保存导入导出，不出现虚假的游戏执行成功提示。

### 阶段二：服务端接入

- 确定管理鉴权和连接配置。
- 对接装备查询、发放和已有管理能力。
- 在服务端新增参数覆盖及实时多杆快照能力。
- 验证远程部署、队列执行状态和断线恢复。
- 提供 Web 构建及部署配置。

验收：浏览器和服务端可分处不同设备；真实能力与不支持能力明确区分。

### 阶段三：Windows 客户端分析

- 确认运行时、资源格式和加载方式。
- 确认模型皮肤、移速、灯光和参数同步的实际入口。
- 决定本地助手与客户端扩展的通信方式。
- 最终选择桌面壳与本地实现技术。

### 阶段四：桌面增强与双端验证

- 复用前端打包 Windows 应用。
- 增加目录、进程、资源和客户端能力。
- 增加独立雷达窗口。
- 验证 Web 配对本地助手的可行性与支持范围。
- 完成版本兼容、备份恢复和发布流程。

## 13. 验证策略

UI 阶段重点检查：

- TypeScript 类型检查及生产构建。
- 页面导航、参数校验和修改状态。
- 预设导入校验、持久化和重置。
- 模拟/真实模式隔离。
- 空数据、加载、错误、离线和不支持状态。
- 浏览器缩放、窄窗口和键盘基本操作。

真实接入阶段增加：

- 管理鉴权与命令完成状态。
- 跨设备部署和反向代理。
- 多杆、多钩、断线重连、入护与放生。
- 客户端修改实际效果和恢复默认。
- 桌面与 Web 使用同一接口时的行为一致性。

## 14. 当前决策与待确认事项

已明确的方向：

- 同时提供 Web 和 Windows 桌面两种形态。
- 共用前端与业务接口。
- 分离服务端连接和 Windows 客户端连接。
- 先实现 UI 与 Mock，后接真实逻辑。
- 服务端操作通过 API，不让前端直接修改数据库。

待后续验证：

- 桌面壳最终选择。
- 客户端插件/扩展技术和助手实现语言。
- Web 到本地助手的浏览器兼容范围。
- 全部可编辑字段及双端同步方式。
- 真实模型预览与资源替换流程。

当前不存在阻碍 UI 开发的客户端分析依赖；尚未确认的游戏能力以占位、模拟或不支持状态表达。
