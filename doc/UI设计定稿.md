# RF4 工具包 UI 设计定稿

## 1. 当前决定

- **A 双工作空间**作为主结构。
- **D 修改清单**只用于保存后的修改记录、前后值查看和回滚，不作为修改前审批流程。
- 编辑页直接保存，不要求跳转清单、勾选审批或逐级确认。
- 默认亮色，支持海蓝、森林绿、暖砂三套亮色配色。
- 当前仅确定 UI 设计；先到 Windows 运行游戏并分析客户端，之后再实现正式前端和业务。

本文件为当前唯一 UI 设计依据。字段归属、范围及真实回滚能力仍待分析，不因 UI 定稿而视为已验证。

当前预览：`doc/design/index.html`（相对项目根目录）。HTML 内的少量交互仅展示设计，无真实连接、存储接口或游戏修改。

## 3. 双工作空间与执行边界

| 空间 | 入口 | 目标 | 功能 |
| --- | --- | --- | --- |
| 服务端 | Web | Windows/Linux/macOS/Docker 服务端，可位于远端 | 服务端参数、装备定制与发放、上鱼状态、连接权限 |
| 客户端 | 本地 Web 或 Windows 应用 | 游戏客户端所在的 Windows 电脑 | 客户端参数、模型皮肤、人物移速、灯光、本地备份 |

- 两端可以不在同一台机器，连接和可用性独立。
- 服务端保存和回滚不依赖客户端助手。
- 客户端本地 Web 由本机助手提供；应用可通过本地模块提供能力。
- 远端服务端网页不能被默认视为具有本机修改权限。
- 涉及双端的功能按实际字段归属拆分，不做一个跨端原子保存或自动回滚的承诺。

原型示例：服务端 `reef-server / Linux / Docker / 192.168.1.20:9500`；客户端 `ANGLER-PC / Windows`。这些都是演示目标。

## 4. A 主结构

```text
顶部：工具名称、设计模式、亮色主题选择
      服务端空间 / 客户端空间
                ↓
左侧：当前空间功能导航
右侧：目标设备条 → 编辑内容 → 直接保存
                ↓
修改清单入口：查看当前空间已经保存的记录与回滚
```

目标设备条始终写明机器、所属端、入口、地址或本机标识、连接状态。不能仅靠颜色区分端。

| 服务端导航 | 客户端导航 |
| --- | --- |
| 装备参数 | 人物与灯光 |
| 定制装备与发放 | 模型与皮肤 |
| 上鱼面板 | 客户端参数 |
| 连接与权限 | 本地连接与备份 |
| 修改清单与回滚 | 修改清单与回滚 |

切换空间保留未保存编辑，但不自动保存、不执行另一端操作。主题切换仅改变视觉，不影响目标、草稿与连接。

## 5. 保存交互：不做审批

```text
编辑当前空间参数
    ↓
字段校验、检查该端连接与能力
    ↓
点击“保存修改”直接提交
    ↓
反馈执行状态，自动生成修改记录
    ↓
用户可按需打开修改清单，而非必须经过清单
```

- 保留字段校验、鉴权和能力检查；它们不是人工审批。
- 不设“待审批数量”“先审阅才允许保存”“已核对后勾选”等关卡。
- 普通参数保存不弹出额外审批窗口。
- 未保存内容可“放弃未保存编辑”，与已保存修改的回滚区分。
- 当前原型保存只更新本页内存；正式系统必须区分已受理、执行中、完成和失败，不能把队列受理当成修改完成。

## 6. D 修改清单：保存后查看

清单默认只展示当前空间、当前目标的已保存记录，不是待执行队列。

每次操作展示：

- 时间、操作编号、目标设备与入口。
- 修改对象、字段和作用范围。
- 修改前值、修改后值及单位。
- 执行结果、是否支持回滚、回滚状态。
- “回滚此项”和“回滚本次修改”。

无记录时提示“保存后自动生成修改记录”，不提示用户去审批。

## 7. 回滚设计

### 目标交互

- 单项回滚：恢复指定字段到该记录的修改前值。
- 整次回滚：恢复一次保存中尚未回滚的字段。
- 回滚按端和目标执行，不隐式修改另一台机器。
- 回滚后保留原记录，标明已回滚；正式系统应另记恢复操作的时间、操作者与执行结果。

### 保护规则

- 已回滚字段不能重复执行。
- 当前值不等于该记录的修改后值时，提示存在后续修改，不直接覆盖。
- 同字段有未保存编辑时，先保存或放弃草稿，避免恢复动作把草稿悄悄清掉。
- 目标端离线或缺少本地能力时，保留记录并说明暂不可回滚；其他端仍独立可用。
- 不支持可逆操作时明确标注不可回滚，不承诺物品发放、消耗或资源替换等所有行为均可简单还原。
- 真实字段需要版本/并发检测、快照和备份。具体实现待 Windows 分析，不在本轮开发。

当前原型演示单项、整次回滚和基础冲突提示，只恢复页面内模拟值，不具备真实游戏备份恢复能力。

## 8. 视觉规范

| 主题 | 背景与文字 | 强调色 |
| --- | --- | --- |
| 海蓝（默认） | 冷白、浅灰、墨蓝文字 | 蓝色 |
| 森林绿 | 淡绿中性色、白面板、深绿文字 | 森林绿 |
| 暖砂 | 米白、暖灰、深棕文字 | 棕金 |

- 所有主题保持亮色，不要求本阶段制作深色。
- 页面、侧栏、表单、记录列表的背景、边框、文字、焦点和强调色统一切换。
- 成功、警告、错误使用独立语义及文字，不能只靠颜色。
- 系统字体、8px 间距节奏、清晰表单与目标信息，避免营销式大标题。
- 窄屏收拢侧栏，参数和记录转单列，不隐藏目标端等关键信息。
- 原型提供标签和焦点样式，正式实现需完整检查键盘操作和 WCAG 对比度。

## 9. 当前阶段不做什么

- 不创建 React/Vite、桌面应用或本地助手工程。
- 不安装正式前端依赖。
- 不接管理 API、数据库、文件系统或游戏进程。
- 不编写真实保存、回滚、资源替换或运行时修改逻辑。
- 不将原型里的示例字段当作已验证能力。

本次修改仅涉及设计文件及其展示交互。主题、编辑值和记录只存在页面内存，刷新重置。

## 10. Windows 分析后补齐

1. 真实字段、单位、范围，以及服务端/客户端/双端归属。
2. 参数实际生效时机，是否需要重载、换装备或重启。
3. 游戏资源格式、外观映射及能否预览模型。
4. 本地助手、客户端扩展与桌面宿主分工。
5. 执行完成反馈、错误与版本兼容信息。
6. 可回滚范围、基线采集、冲突检测、备份恢复策略。
7. 上鱼状态与竿位、快捷键和耐力数据的真实映射。

完成这些分析后，再依据本设计实现正式前端与适配逻辑。
